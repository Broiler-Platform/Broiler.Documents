# Office issue #236: DOCX pages one side draws blank

The DOCX samples of issue #236 where one renderer drew a page blank and the
other inked it, plus two content differences. I rendered each one locally
against the LibreOffice 24.2 reference PDFs, with the reference fonts
(`--font-dir fonts/0`). I counted ink per page (pixels darker than 50%) at
96 dpi. To check for regressions, I re-rendered every corpus sample that uses
a changed feature with the build before and after the change. I scored each
render as the number of ink pixels that do not match the reference, with a
2 px tolerance. Seven samples were analysed in the
[issue #234 note](office-issue-234-docx-blank.md). I re-checked the blocker
recorded there for each one.

| Sample | Cause | Outcome |
| --- | --- | --- |
| `ooxmlexport/data/fdo79968.docx`, `ooxmlexport/data/fdo80523_pptm.docx`, `ooxmlexport/data/fdo80523_sldm.docx` | The previews of these embedded presentations are EMF files that draw their words with `EXTTEXTOUTW` in an `EXTCREATEFONTINDIRECTW` font. `EmfRasterizer` drew no text. | Fixed. `EmfRasterizer` now reads `EXTCREATEFONTINDIRECTW`, which it selects with `SELECTOBJECT`. It also reads `SETTEXTCOLOR`, `SETTEXTALIGN` (left, right and centre; top, baseline and bottom; `TA_UPDATECP`), `SETBKCOLOR` with `ETO_OPAQUE`, `EXTTEXTOUTW` and `EXTTEXTOUTA`. Text is positioned through the window/viewport mapping and the world transform, and the font's escapement rotates the baseline. Each character is placed at the record's own `Dx` offset, except in scripts that shape across characters, which are drawn as one run. Records that hold glyph indices (`ETO_GLYPH_INDEX`) are skipped. The text is drawn by `BImageRenderer` onto a transparent layer, which is composited in record order. Fonts therefore go through the same process-wide font resolution as the page, so the reference's Carlito replaces Calibri. A stock font object clears the selection. Ink went from 0/0 to 1279 against 1115 for `fdo79968`, and to 360 against 316 for both `fdo80523` samples. |
| `ooxmlexport/data/fdo78384.docx`, `ooxmlimport/data/tdf103664.docx` | `w:sym` characters in Wingdings, which the reference font set does not have. The reference PDF is not empty: it embeds DejaVu Serif and draws the characters as that face's `.notdef` glyph. A local pdftoppm draws them as boxes (tdf103664: 126 ink pixels). The CI's pdftoppm 24.02 paints nothing for `.notdef`, so the page reads as blank there. broilerdoc draws the graphics stack's fallback "?" in the same place. | Not changed. LibreOffice does draw something here, a missing-glyph box, so drawing nothing for a private-use character the face lacks would not match LibreOffice, only one rasterizer's rendering of it. It would also hide content that Word, and a LibreOffice that has Wingdings, draw as ✓➲①. The closer match is a notdef box instead of "?", which is a Broiler.Graphics change. A Wingdings-to-Unicode table, as `SymbolFontText` recodes Symbol, would draw the real symbols. |
| `ooxmlexport/data/TextFrameRotation.docx`, `ooxmlimport/data/tdf125038b.docx`, `ooxmlexport/data/tdf104115.docx` | LibreOffice import behaviour that 26.2 still has, as the issue #234 note shows. | Not changed. `tdf125038b.docx` gains one change from the field fix below: its result now starts the first line, as LibreOffice's text export has it. The page is still inked where LibreOffice's is blank. |
| `ooxmlimport/data/tdf122717.docx` | A vertical `prstGeom line` with `<a:ln w="0">`, a hairline. The painter drew a zero-width outline 0.25 pt wide. At 96 dpi that band fell between pixel centres, so nothing was drawn. LibreOffice draws a hairline one device pixel wide. | Fixed. `DocumentPagePainter.HairlineWidth` is 0.75 pt, one pixel at 96 dpi, for zero-width outlines, rules and segments. The page went from blank to the reference's line (mismatch 310 to 0). `rtfimport/data/tdf115153.rtf` (zero `\dplinew`) also went from 50 to 0. Of the 34 corpus samples with zero-width lines, `tdf99810-lost-arrow.odt` scores worse (58 to 117): LibreOffice antialiases its hairline to light grey, which falls below the ink threshold, and broilerdoc's is solid. |
| `uiwriter/data/tdf131963.docx` | Page 3 lies inside a continuous section whose first paragraph opens with a page break. That section has a page-number footer and, through `w:titlePg`, an empty first-page footer. The layout treated the page the break opens as the section's first page, so it drew the empty footer. A continuous section starts on the page its break is on, so the page its first page break opens is its second page. LibreOffice and Word draw "3" there. | Fixed in `DocumentLayout`. A continuous section that a paragraph's page break opens now shares its first page, as it already did for a break later in the section. Page 3 now has its number (29 ink against 33), centred where LibreOffice centres it but at the left: the footer's `w:framePr` (`xAlign="center"`, `hAnchor="page"`) is not honoured, which is a separate gap. `uiwriter/data/tdf129805.docx` now draws its page-2 number too. `DocumentLayoutSectionRunningTests.A_Sections_First_Page_Part_Is_For_Its_First_Page_Not_The_Documents` relied on the model's default `Continuous` break for what is a new-page section, so it now states `NextPage`. |
| `layout/data/tdf115094.docx`, `ooxmlimport/data/tdf115094v2.docx` | Two problems. First, both logos are TIFFs (LZW with horizontal differencing), and the TIFF codec read only uncompressed strips, so nothing was drawn. Second, the pictures are in table cells with `layoutInCell="1"` and `positionV relativeFrom="page"`. LibreOffice measures "page" from the cell there (tdf#115094), but broilerdoc measured it from the page top. | Fixed. `TiffImageCodec` now decodes LZW (TIFF 6.0 §13, early code-width change) and PackBits, horizontal differencing (predictor 2), and RGBA with `ExtraSamples` alpha. A page-relative floating picture laid out in its cell hangs from the cell's first paragraph (`DocxDocumentBuilder.CellParagraphIndex`), with a horizontal `column` offset taken from the cell. Mismatch went from 679 to 22, and both logos and the wheelchair icon now sit in the table. Remaining differences: LibreOffice wraps "Zufahrt für" around the icon, but broilerdoc does not wrap text in a cell around a float. This applies only to pictures and only to `page`. LibreOffice 24.8 does the same for drawn shapes and the page margin (tdf#160077, `tdf160077_layoutInCell*.docx`). The 24.2 references do not, so applying it there scored `tdf160077_layoutInCellB.docx` more than twice as far off (67 054 to 155 781). That is left for when a reference-defect row for tdf#160077 can cite the fixing commits. `tdf128646.docx` now has its page-relative picture at LibreOffice's cell height, but horizontally it is still page-aligned (`align right` against the page), where LibreOffice aligns it with the cell. |
| `globalfilter/data/fieldmark_QUOTE_nest.docx` | A `QUOTE` field nested in another `QUOTE`, with both instructions running over seven paragraph marks. Paragraph marks inside an instruction are field code, which Word does not show and LibreOffice's import drops (tdf#125038). broilerdoc kept them as eight empty lines above the result. LibreOffice's text export lists the inner field's result ("foo", "bar", "baz") inside the outer instruction, but its PDF does not draw it. | Fixed (layout). When a paragraph ends with a field still in its instruction, the next paragraph continues it (`DocxDocumentBuilder.JoinsFieldCodeParagraph`). This does not happen in table cells, in a paragraph that ends a section, or across a table. It stops after 64 joined marks, so a field that never ends does not fold the rest of the document into one paragraph. The result now starts the page as in LibreOffice's PDF (mismatch 879 to 487). The three text-check lines remain: they come from LibreOffice's text export, which disagrees with its own PDF and with Word. `tdf125038_conditionalText_DOCPROPERTY.docx` also improved (1558 to 941). |
| `ooxmlexport/data/sdt-picture-databinding.docx` | A picture content control whose `w:dataBinding` points at base64 PNG data in custom XML. LibreOffice 24.2 replaces the drawing with the base64 text. broilerdoc draws the picture. | Not changed. The upstream test `ooxmlexport27.cxx testSdtPictureDataBinding` states that, without the fix, the drawing was replaced by the raw base64 text. So the reference shows a fixed LibreOffice defect. I could not identify the fixing commit or its release, so there is no reference-defect row yet. |

## Verification

- Ink per page, broilerdoc against LibreOffice 24.2, before and after:
  `fdo79968` 0 to 1279 (LibreOffice 1115); both `fdo80523` 0 to 360 (316);
  `tdf122717` 0 to 309 (310); `tdf115094` and `tdf115094v2` 0 to 531 (434);
  `tdf131963` page 3 0 to 29 (33). `fieldmark_QUOTE_nest` keeps its ink (389 against 347) and moves
  to the top of the page. `fdo78384` and `tdf103664` are unchanged (1752 and 254;
  LibreOffice's notdef boxes 1342 and 126 with a local pdftoppm).
- Regression sweeps, before and after, scored against the references:
  - All 70 DOCX samples with EMF text. 32 changed, 26 of them closer to the
    reference. The 6 that scored worse (`tdf99631.docx` twice, `fdo80410.docx`,
    `tdf122563.docx`, `skipimage-embedded-document.docx`,
    `embedded-xlsx.docx`) are previews whose text LibreOffice clips or does not
    draw. broilerdoc now draws what the metafile states, where it used to draw
    a placeholder box or nothing.
  - 34 samples with zero-width outlines.
  - 34 samples with continuous sections that own headers, page-relative
    floats in cells, TIFF media, or field instructions over paragraph marks.
- Tests: `DocxOfficeIssue236Tests` (EMF text, field-code paragraphs,
  page-relative pictures in cells), `TiffImageCodecTests` (LZW with predictor,
  code-width growth, PackBits), `DocumentPageDrawingGeometryTests` (hairline),
  `DocumentLayoutSectionRunningTests` (continuous section opened by a page
  break). Docx (970), Pagination (419), core (323), Cli (346), Odt (666), Rtf (640),
  Office (95) and Pdf (749) test projects all pass.
